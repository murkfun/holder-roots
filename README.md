# murkfun-holders

Check [MurkFun](https://murk.fun)'s holder set yourself.

Every MurkFun order proves, in zero knowledge, that the wallet that signed it is in the **holder set**: a Poseidon2
Merkle tree of the wallets that hold a SPACE ID Agent ID on BNB Smart Chain (claimed through the Binance Agentic
Wallet). The tree lives on chain in `MurkFunHolderRoots`; MurkFun's operator adds new holders in batches, and anyone
can check every batch, remove a wrong entry with a fraud proof, or force a missing holder in. This package is the code
to do that, with nothing to trust but the chain and SPACE ID's registration signer (see the trust assumption under
[Security model](#security-model)):

- rebuild the whole tree from the contract's `Batch` events and compare every root with the contract's;
- look up a holder (address, name or name.ai) and get its batch, position, status and Merkle path, each checked on
  chain;
- audit the set against the SPACE ID registry (listed non-holders, admin-minted entries, missing holders);
- send the fraud proofs (`challenge`, `disputeOrigin`) and forced inclusions (`enqueue`) yourself;
- verify that the deployed contracts are exactly the sources in [contracts/](contracts).

The live set: https://murk.fun/holders. Version 1.0.0 targets the MurkFun contracts v1.1 on BNB Smart Chain (the
holder set below). MIT licensed, except `contracts/src/verifiers/BatchVerifier.sol` (Apache-2.0, © Aztec, generated by
Barretenberg; [LICENSES/Apache-2.0.txt](LICENSES/Apache-2.0.txt)) and `contracts/lib/openzeppelin-contracts` (MIT,
© Zeppelin Group); see [LICENSE](LICENSE).

```bash
npm install -g https://github.com/murkfun/holder-roots/releases/latest/download/murkfun-holders.tgz
murkfun-holders tree                     # rebuild the tree, compare every root with the contract's
murkfun-holders lookup <name>.ai         # or a 0x address
murkfun-holders status
```

## Why it exists

MurkFun's privacy rests on two things: an order proves its signer is *some* holder without saying which, and the set
of holders is exactly the SPACE ID Agent ID holders that claimed through the user path. If the operator could add an
address of its choosing, it could trade as anyone; if it could leave holders out, it could censor them. So the set is
built to be checked by anyone, from public data only, and corrected by anyone, on chain.

## Security model

**Governance today.** `MurkFunHolderRoots` has no timelock and no pause: `setParams` and `setOperator` apply
immediately. The owner and the operator are currently the same EOA (`0x7EB4E00c640F56A395a678d927f8bED75b66A84C`),
not a multisig. The owner can shorten the challenge window of new batches to 10 minutes (`MIN_CHALLENGE_PERIOD`) and
raise `DISPUTE_DEPOSIT` without limit (up to 2^96 wei); `MIN_BOND` is 0, so no bond is at stake. `murkfun-holders
status` shows all of these (`owner`, `operator`, `ownerIsOperator`, `minBondWei`, `disputeDepositWei`,
`challengePeriodS`). The MurkFun market and factory contracts are governed separately: a 24 h timelock on owner
changes and a separate pause guardian; their owner is not a multisig yet either. Neither covers this contract.

| Who | Can | Cannot |
|---|---|---|
| Operator (posts batches; unbonded on mainnet: `MIN_BOND` = 0) | add the next batch of 1–1024 addresses, at its own cadence; stop posting (a stall: the forced-inclusion queue waits too, as nobody else can post) | add anything that is not in the published list (the batch proof binds the new root to exactly the list in the `Batch` event); keep a non-holder in (anyone's `challenge`, at any time); keep an admin-minted address in, if someone disputes it in time (anyone's `disputeOrigin`, only inside the batch's challenge window); leave a registered holder out while it keeps posting (anyone's `enqueue`: the next batches must include it after `QUEUE_GRACE`, 1 h) |
| Owner (Ownable2Step; today the same key as the operator) | replace the operator; set `CHALLENGE_PERIOD` (≥ 10 min), `ROOT_HISTORY` (≥ 1), `MIN_BOND` and `DISPUTE_DEPOSIT` (no floor, up to 2^96 wei), all effective at once | add or remove a holder; make a posted root usable before `postedAt + MIN_CHALLENGE_PERIOD`; change the window or deposit of a batch or dispute already open |
| MurkFun's holder-set API | answer lookups fast | make this package report anything as verified that the chain does not confirm |
| You | everything in this package, with any BSC endpoint | — |

Details:

- **Tree.** Depth 26: 2^16 batch slots of 2^10 leaves; batch `id` fills slot `id`, zero-padded. `leaf(A) = H(A)`, an
  empty leaf is 0, `H` is Poseidon2 over BN254 (Noir's, the same as the circuits). The empty tree's root is hard-coded
  in the contract (`EMPTY_ROOT`). Code: [src/tree.mjs](src/tree.mjs).
- **Batches.** `postBatch` takes strictly increasing addresses and a proof of the batch circuit
  ([circuits/batch](circuits/batch)) that `newRoot = append(oldRoot, addrs)` with every address a public input.
- **Challenge window.** A batch's root is usable by orders from its `usableFrom` (posting time + `CHALLENGE_PERIOD`,
  1 h on mainnet) and not while an origin dispute of it or an earlier batch is open. `acceptedRoot()` is the root
  orders prove against.
- **Fraud proofs.** `challenge(id, index, addrs, salt)`: the listed address holds no Agent ID (checked by the
  contract on the spot; the Agent ID is soulbound, so this never succeeds against a holder). `disputeOrigin` +
  `resolveOrigin`: the listed address has no SPACE ID `register` signature (anyone can answer a dispute with it).
  Success drops the batch and every later one and pays the operator's bond to the challenger (the bond is 0 on
  mainnet, so a fraud proof earns nothing and costs gas, plus `DISPUTE_DEPOSIT` for a dispute, 0 today, returned to
  whoever wins it). Both are commit-reveal (`commit` a block earlier), so a copied transaction earns nothing.
  `challenge` works at any time; `disputeOrigin` only while the batch is in its challenge window (the contract's NatSpec
  summary "fraud proofs, any time" is about `challenge`): an admin-minted entry nobody disputes in that window stays.
- **Forced inclusion.** `enqueue(addr, deadline, sig)` with the address's own `register` signature (read from its
  registration transaction): free, once per address, ever.
- **Known limitation: origin disputes that outlive their batch.** A batch dropped by a fraud proof leaves its open
  origin disputes open, and `resolveOrigin` matches a dispute to the batch now in its slot by `postedAt` and
  `listHash` only, not by the batch's serial. A replacement batch in the same slot with the same list, posted in the
  same second as the dropped one, would therefore be dropped when such a stale dispute is resolved. The contract is
  deployed and does not change; the off-chain side avoids it:
  - MurkFun's operator software never posts into a slot at a block time equal to the `postedAt` of the batch dropped from it or
    of any open dispute of that slot: it waits until the chain's latest block time is past that second
    ([src/disputes.mjs](src/disputes.mjs) `postedAtToAvoid`, `waitPast`). A replacement then never matches a stale
    dispute, and resolving one only returns its deposit (`DisputeVoid`).
  - Stale disputes are closed early: the operator answers them like any dispute (`defendOrigin`, with the holder's
    registration signature, at any time), and both the operator and the audit (`--challenge`) resolve every stale one,
    whoever opened it, as soon as its answer window has passed.
  A different operator key or software that reposts a slot within the same second would not have this protection; the
  worst case is that its replacement batch is dropped and its holders go back into the next batches (no holder can be
  added or kept out by it).
- **Trust assumption.** SPACE ID signs `register` only for Binance Agentic Wallets. The set can not hold an address
  without an Agent ID once someone checks, nor an admin-minted one if someone disputes it inside its batch's window.
  It can be delayed by an operator that stops posting; the remedy is the owner's `setOperator`, and today the owner is
  the same key, so a stall lasts until that key posts again or hands the role on.

- **Names in the contract's comments.** The NatSpec of `MurkFunHolderRoots.sol` (byte-identical to the deployed,
  verified source, so it is not edited here) names files of MurkFun's development tree. Their public counterparts:
  `docs/SIGNED_ORDERS.md` is [docs/SIGNED_ORDERS.md](https://github.com/murkfun/murkfun-mcp/blob/main/docs/SIGNED_ORDERS.md)
  of the MCP repository; the `core.mjs` named for the empty tree (`ZEROS`) is [src/tree.mjs](src/tree.mjs); the
  holders-audit script is [src/audit.mjs](src/audit.mjs) (`murkfun-holders audit`);
  `test/utils/HandleRegistry.sol` is the registry's verified source on BscScan; "the sync bot" is MurkFun's operator
  service. "a bonded operator" and "slashes the whole bond" describe what the contract supports; on mainnet the bond
  is 0 (above).

## Verify it yourself, step by step

You need the `murkfun-holders` command ([Install](#install)) and, for step 4, [Foundry](https://getfoundry.sh). Use your own BSC endpoint if you have one: it
must serve `eth_getLogs` over old blocks (the default, `https://public-bsc.nownodes.io`, does; `bsc-dataseed`
endpoints do not). Two endpoints (`--rpc a,b`) are cross-checked against each other.

1. **The contract's state.** `murkfun-holders status`: batch count, the accepted and current roots, the
   challenge window, the forced-inclusion queue, the owner and the operator (`ownerIsOperator`), `MIN_BOND` and
   `DISPUTE_DEPOSIT`.
2. **The tree.** `murkfun-holders tree`: reads every `Batch` event of `MurkFunHolderRoots`, recomputes each
   batch's subtree root and the tree root after it from the published addresses, and compares them with the event,
   with the contract's stored root and list hash, and the final current / accepted roots with `currentRoot()` /
   `acceptedRoot()`. It exits 1 on any difference.
3. **One holder.** `murkfun-holders lookup <0x address | name | name.ai>`: the Agent ID's owner and handle (from
   the registry), how it was minted (`register`, in the set, or `adminRegister`, never in it: from the registration
   transaction's receipt), its batch and position (from that batch's `Batch` event, whose list hashes to the
   contract's), whether the batch is accepted, `usableFrom`, and the Merkle path to the accepted root, checked
   against `acceptedRoot()`. `verified` says what was checked on chain; MurkFun's API (`https://murk.fun`) is only
   used to find things faster (it sees the address you look up, with your IP address), and `--no-api` reads
   everything from the chain.
4. **The code.** `npm run verify-bytecode` (in a checkout of this repository): compiles [contracts/](contracts) with
   the deployment's settings (solc 0.8.28, optimizer 200 runs, cancun) and compares the runtime code with the code at
   the two addresses below, without the CBOR metadata tail and with the constructor's immutables zeroed (it then
   checks those immutables in order: the Agent ID registry, the batch verifier and the registry's EIP-712 domain, read
   from the deployed code). The source is also verified on Sourcify and BscScan:

   | Contract | Address | Sourcify | BscScan |
   |---|---|---|---|
   | MurkFunHolderRoots | `0xD59867DADC96202284Fa54d016C6d66a0adBaE24` | [repo.sourcify.dev](https://repo.sourcify.dev/56/0xD59867DADC96202284Fa54d016C6d66a0adBaE24) | [bscscan.com](https://bscscan.com/address/0xD59867DADC96202284Fa54d016C6d66a0adBaE24#code) |
   | BatchVerifier (UltraHonk, generated by Barretenberg) | `0x3BA574b3d102800c3E08E2F978A4d802C15b8C9E` | [repo.sourcify.dev](https://repo.sourcify.dev/56/0x3BA574b3d102800c3E08E2F978A4d802C15b8C9E) | [bscscan.com](https://bscscan.com/address/0x3BA574b3d102800c3E08E2F978A4d802C15b8C9E#code) |
   | SPACE ID Agent ID (HandleRegistry) | `0x60B9262456dE011F7d15a54CdD8c48bAaa8B022F` | [repo.sourcify.dev](https://repo.sourcify.dev/56/0x60B9262456dE011F7d15a54CdD8c48bAaa8B022F) | [bscscan.com](https://bscscan.com/address/0x60B9262456dE011F7d15a54CdD8c48bAaa8B022F#code) |

5. **The registry.** `murkfun-holders audit`: rescans every SPACE ID registration and every batch and reports
   listed addresses without an Agent ID (`extra`), admin-minted entries (`adminMinted`), registered holders missing
   for longer than the grace period (`missing`, 24 h by default) and root mismatches. Exit 0 clean, 1 extra /
   admin-minted / mismatch / RPC disagreement, 2 missing only. A full scan of the registry is several thousand
   `eth_getLogs` calls: minutes, at the default 4 requests per second (`--rps`).

## Acting on what you find

Nothing is sent without `--key-file <file>` (a file holding a funded key, 0x + 64 hex digits; never pass a key on the
command line) **and** `--yes`; without them both commands are dry runs:

```bash
murkfun-holders challenge --rpc https://a.example,https://b.example            # dry run: what it would send
murkfun-holders challenge --rpc https://a.example,https://b.example --key-file ./key --yes
murkfun-holders enqueue <name>.ai                                               # dry run (simulated)
murkfun-holders enqueue <name>.ai --key-file ./key --yes
```

Before sending, both check that the endpoint is BNB Smart Chain (chain id 56; `--chain-id` for a test chain) and that
its gas price is at most `--max-gas-price-gwei` (default 5). Each `disputeOrigin` sends the contract's
`DISPUTE_DEPOSIT` (0 today; the owner can raise it): only up to `--max-deposit` BNB (default 0.05). The dry run of
`challenge` shows the number of transactions and the deposit (`plan`). `challenge` exits 1 when any step failed or was
refused.

`challenge` runs the audit and sends, for the first listed non-holder, `commit` then `challenge`; for each admin-minted
entry still inside its batch's window, `commit` then `disputeOrigin`; and `resolveOrigin` for disputes whose answer
window has passed. It needs two or more endpoints that agree. `enqueue` finds the holder's `register` signature in its
registration transaction, checks it with the contract's `registrationSigner` view, simulates and then sends
`enqueue`. `audit --interval-s 600` repeats the audit and alerts through a webhook (`ALERT_WEBHOOK_URL`,
`ALERT_DISCORD_WEBHOOK_URL`); add `--challenge --key-file <file> --yes` to send the fraud proofs without a human in
the window (the same limits apply). `lookup` and `enqueue` ask MurkFun's holder-set API first unless given `--no-api`;
`murkfun-holders --help` lists every option.

## As a library

```js
import { HolderSetReader, holderPath, rootFromPath, leaf } from "murkfun-holders";
const r = new HolderSetReader({ rpc: "https://public-bsc.nownodes.io" });
const t = await r.tree();            // { ok, batches, rebuiltAcceptedRoot, acceptedRoot, mismatches, ... }
const h = await r.lookup("0x…");      // or "<name>.ai": { member, batch, position, accepted, path, verified, ... }
```

Subpaths: `murkfun-holders/tree`, `/chain` (log scanning with range splitting, rate limits and cross-checks),
`/lookup`, `/audit`, `/registration`, `/disputes`, `/network` (the addresses above).

## Layout

| Path | |
|---|---|
| `src/tree.mjs` | Leaf, node, empty roots, batch subtrees, the global tree, paths, the batch circuit's witness |
| `src/chain.mjs` | Log scanning (registrations, batches), balances, cross-checks between endpoints |
| `src/lookup.mjs` | Contract state, one batch's list, the tree rebuild, a holder's lookup |
| `src/audit.mjs` | The audit and the fraud proofs it sends (`--challenge`), its watch mode |
| `src/registration.mjs` | A holder's `register` signature from its registration transaction |
| `src/disputes.mjs` | Origin disputes that outlive their batch: which are stale, the block time a slot must not be posted at |
| `src/alerts.mjs` | Webhook alerts of the watch mode |
| `src/entry.mjs` | How the scripts tell they were started directly (any path) |
| `src/cli.mjs` | The `murkfun-holders` command |
| `src/network.mjs` | The deployed addresses and deploy blocks |
| `contracts/` | `MurkFunHolderRoots.sol`, `verifiers/BatchVerifier.sol` and exactly the OpenZeppelin 5.4.0 files they import, byte-identical to what was deployed; `bytecode.json`: the expected hashes |
| `circuits/batch`, `circuits/lib` | The batch circuit (Noir 1.0.0) and the library it uses |
| `scripts/verify-bytecode.mjs` | Build + compare with the chain |

| `LICENSE`, `LICENSES/` | MIT; the Apache-2.0 text for `BatchVerifier.sol` |
| `test/` | `npm test` (no network) |
